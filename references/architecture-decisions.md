# 技術與資料決策

先從使用情境推導，不先要求使用者選技術。

## 平台

| 情境 | 優先建議 | 轉向其他方案的條件 |
|---|---|---|
| 手機與電腦都要、主要是表單／查詢／內容 | 響應式 Web + PWA | 需要深度相機、藍牙、背景定位或商店分發時評估原生／跨平台 App |
| 只在固定桌機或 NAS 內網用 | 本機 Web | 需要外出存取時再加安全遠端入口，不直接暴露 NAS |
| 完全單機、無需瀏覽器 | 桌面程式或本機 Web | 依維護能力選擇，不為「像 App」增加無必要複雜度 |
| 需要 App Store、深度裝置能力 | 原生或跨平台 App | 後端資料與權限仍需獨立設計 |

「加入主畫面」不是完整 PWA 的充分證據。至少驗收 manifest、圖示、HTTPS、standalone、合理離線狀態和快取更新策略。

## 資料真相

| 選項 | 適合 | 不適合／限制 |
|---|---|---|
| Markdown／檔案 | 文字知識、少量關聯、可攜與人工可讀 | 複雜查詢、多人同時寫入、細緻權限 |
| localStorage | 丟棄式原型、偏好設定、快取 | 私人重要資料、跨裝置同步、可靠備份；不可當正式資料真相 |
| IndexedDB | 瀏覽器離線、大量本機資料、可重建快取 | 多裝置權威同步仍需後端與衝突策略 |
| SQLite | 單人或小型本機服務、結構化查詢、低維護 | 多台裝置直接共用檔案或多人併發；應由服務層存取 |
| 伺服器資料庫 | 多使用者、跨裝置、角色權限、稽核 | 需要登入、備份、遷移、監控與持續成本 |
| 雲端託管資料庫 | 快速取得跨裝置與託管能力 | 供應商成本、資料位置、出口與離線需求 |
| 記憶體／假資料 | 視覺原型與教學 Demo | 不能宣稱持久化；重啟即失去資料 |

AI 可以幫忙設計 schema、migration 與假資料，但「AI 自己生成資料庫」仍必須落到上述真實儲存、備份、權限和還原機制。

## 部署

- **單機**：明確資料檔位置、啟動／停止、更新與本機備份。
- **NAS／內網**：容器或服務生命週期、權限、磁碟備份、HTTPS、VPN／私網入口；不要直接公開管理埠。
- **雲端**：登入、租戶隔離、秘密管理、成本上限、日誌、備份與回復演練。
- **混合**：定義唯一資料真相、同步方向、離線衝突和失聯時行為；不要讓兩邊都可無規則寫入。

## 從 localhost 延伸到手機

`localhost` 只代表目前裝置本身。不要因手機要連線就直接把服務改成監聽 `0.0.0.0` 或暴露到公開網路。

1. 先查實際程序、工作目錄、連接埠、監聽位址與防火牆。
2. 若使用 SQLite，資料檔留在服務端，由受保護 API 存取；不要把 SQLite 檔案直接同步或分享給手機。
3. 分開評估同一 Wi-Fi、VPN／私網入口、雲端部署三條路線，說明外出使用、維護與成本差異。
4. 登入、HTTPS、網路限制、秘密管理與備份尚未完成前，不公開服務。
5. 用真實手機驗證連線、重新登入、權限、斷線與服務重啟後的行為。

## 決策輸出

每次只給：

1. 推薦組合與一句理由。
2. 使用者會感受到的好處。
3. 主要限制與月費／維護負擔。
4. 一到兩個備選，以及何時值得切換。
