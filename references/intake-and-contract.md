# 需求訪談與開發契約

## 自然語言與痛點探索

使用者不需要記住 Skill 名稱、提示詞或固定格式。當使用者在工作台脈絡中說「這裡不順」、「想加功能」、「首頁太亂」或「幫我調整一下」，先把它視為工作台需求，從自然語言中整理目前觀察到的問題。

除明確錯誤外，先完成以下順序：

```text
自然語言 → 需求類型 → 痛點選擇題 → 使用情境 → 方案比較 → 開發契約
```

規則：

- 每次只問一個問題。
- 提供 2～4 個白話選項，保留「其他」自由描述。
- 選項要描述痛點或希望結果，不先要求技術決策。
- 使用者選定方案前，不修改產品程式、資料模型、正式 Vault 或部署。
- 明確錯誤直接診斷；不確定是錯誤還是摩擦時，只確認功能是否「沒有作用」或「可以用但不順」。
- 若會改變畫面、互動或響應式行為，方案選定後再搭配 UI／UX Skill；不因 UI 需求跳過痛點確認。

常見選項可依情境挑選：找不到資料、不知道優先順序、進度／阻塞不清楚、忘記後續追蹤、首頁資訊太多、想看成果回顧、想整合資料來源、其他。

## 訪談原則

- 一次只問一題，先問最會改變產品或架構的問題。
- 已有答案就記錄，不換句話重問。
- 使用者不知道技術時，問情境而不是名詞；例如問「是否要在手機與電腦看到同一份資料」，不要先問「要 SQLite 還是 PostgreSQL」。
- 每題可提供 2 到 3 個白話選項，推薦項放第一，但保留自由回答。
- 一條訪談主題若包含同步、離線、匯入、匯出等多個決策，拆成多輪；每輪仍只問一個決策。
- 功能例子最多先給三個，避免把候選功能變成使用者以為必須全做的範圍。
- 若答案只影響細節而不阻擋本版，可標成實作後調整，不拖住開始。

## 建議順序

1. **痛點**：這次最想改善的是找資料、抓重點、追蹤進度、提醒、回顧、整合，還是其他問題？
2. **目標與情境**：誰在什麼時候打開它？希望完成什麼？目前怎麼處理？
3. **方案比較**：提供 2～3 個方案，說明痛點、使用方式、優缺點、範圍與驗收差異。
4. **UI／UX 檢查**：若涉及畫面，確認是否需要設計系統、資訊層級、互動與手機版檢查；純後端不適用。
5. **P0 功能**：若第一版只能完成三件事，必須是哪三件？
6. **平台**：只用網頁、只用手機，或兩者；已確定平台時不要重問，只在會改變技術路線時另問相機、定位、背景服務等原生能力。
7. **版型**：偏資訊密集工作台、今日行動首頁、卡片式儀表板、流程看板，或提供參考圖？
8. **使用者與權限**：只有自己、家庭／團隊，或不同角色；哪些資料不能互看？
9. **設備與部署**：筆電、桌機、手機、NAS、公司網路或雲端；能否長時間開機？
10. **資料行為**：要記什麼、怎麼查、是否跨裝置同步、離線、匯入、匯出與還原？
11. **AI 與整合**：AI 只整理草稿，還是可在核准後寫入？需要通知、行事曆、檔案或其他服務嗎？
12. **成本與維護**：可接受免費、本機維護或固定月費？誰處理備份與更新？
13. **驗收**：第一版完成時，使用者要能親自走完哪三條流程？哪些明確不做？

若使用者已說清楚其中多項，直接跳到第一個缺口。

## 版型核准

在改產品碼前提供 1 到 3 種真正不同的資訊架構或版型方向。若已有核准設計，先做參考／現況對比，說明本輪精確範圍。視覺核准至少包含：

- 桌面主導覽與頁首位置。
- 手機主導覽與最重要按鈕位置。
- 首頁資訊優先順序。
- 主要新增、編輯、查詢與復原流程。
- 可存取性、文字大小、觸控與空狀態方向。
