# 持續演化與教學模式

## 專案演化循環

1. **觀察**：記錄真實使用頻率、最常停住的位置、手動繞路與未使用功能。
2. **分類**：分成錯誤、摩擦、需求、偏好或未驗證想法；不要把每句回饋都升成 P0。
3. **假設**：寫出「若改 X，使用者在 Y 情境會更容易完成 Z」。
4. **最小版本**：一次只改到足以驗證假設，保留回復方式。
5. **驗收**：實際走桌面／手機流程、資料重啟、備份還原與權限邊界。
6. **記錄**：更新 PROJECT_STATE、DECISIONS、FEEDBACK、CHANGELOG。

下次啟動時先回答：現在實際版本是什麼、上一版要驗證什麼、證據如何、這次最小改動是什麼。

## Skill 成長

- 專案特有偏好留在專案狀態，不污染通用 Skill。
- 同一做法至少在多個情境反覆成功，才列為通用候選。
- 候選先記錄「證據、適用範圍、反例、建議修改」，不要靜默覆寫 Skill。
- 更新 Skill 前重新驗證觸發描述、守門條件與舊情境，避免越長越容易誤觸發。

修改通用 Skill 時，使用 [regression-scenarios.md](regression-scenarios.md) 做前向回歸；測試代理只讀檔案，不要在產品專案中實作測試情境。

## 教學模式

只有在使用者要求教學、課程、SOP 或產品素材時使用。先確認教學對象、先備能力與可用時間。每個單元應由一條已驗證的真實流程產生：

```markdown
# 單元名稱
- 學完能完成：
- 使用情境：
- 先備條件：
- 作品／完成證據：

## 先讓學員做
## 明確卡點與第一個提示
## 可直接使用的 Prompt／SOP
## 常見錯誤與復原
## 自我檢查
## 延伸挑戰
```

教學要區分：設計決策、已實作功能、示範假資料、正式資料與尚未完成。不要把規劃頁或漂亮 Demo 宣稱為完整產品。
