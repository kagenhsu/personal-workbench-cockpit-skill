# PM、設計稿、MCP 與 Agent 開發流程

## 目的

網站與行動 App 都先處理產品問題與使用流程，再決定介面、工具連接與實作方式。不要從畫幾張畫面直接跳到開始寫程式

固定流程：

```text
PM Skill → 設計稿 → MCP → Agent 規劃設計 → 開發落地
```

這條流程不是強制使用特定平台，而是每一段都要留下可檢查的交接結果

## 五個階段

### 1  PM Skill：梳理問題與開發規範

先完成：

- 使用者與使用情境
- 反覆處理的課程項目、工作項目、專案項目或選題
- 從紀錄、安排、執行到完成的流程
- 最後要看到的進度、風險、數據或復盤
- P0 功能、明確不做、資料真相、權限與驗收方式

PM 產出短開發契約，不用技術名詞取代問題定義。複雜需求使用 `grill-me` 一次問一題，直到範圍與驗收足夠清楚

### 2  設計稿：把流程變成可操作體驗

設計稿不只畫首頁，至少要說明：

- 網站與行動 App 的主要入口
- 今日重點、全局狀況、判斷建議與任務追蹤如何呈現
- 每個主要操作的開始、確認、成功、失敗、空狀態與返回
- 手機觸控尺寸、鍵盤與無障礙、響應式或原生能力差異
- 資料從哪裡進入、在哪裡修改、何時回寫與如何復原

新頁面或重大改版依序搭配 `ui-ux-pro-max` 與可用的 `impeccable`。五個設計靈感庫只作研究參考，選 1～2 個即可，不複製整套版型或素材

### 3  MCP：接通資料與工具能力

MCP 用來連接可用的資料來源、Agent 或開發工具。使用前先列出：

- 連接名稱與用途
- 可讀取、可寫入與不可碰觸的範圍
- 需要的權限、秘密與成本
- 回傳資料格式與失敗行為
- 是否需要使用者確認後才執行

MCP 不等於自動授權。涉及正式資料寫入、發布、通知、付款、刪除、部署或外部訊息時，仍要先預覽並取得使用者確認。找不到適合的 MCP 時，先以檔案、命令或人工交接完成，不自行虛構連線

### 4  Agent 規劃設計：分工與交接

依任務分派最少必要的 Agent 或工具：

| 角色 | 主要責任 | 交接結果 |
| --- | --- | --- |
| PM | 需求、範圍、優先順序、驗收 | 開發契約 |
| Designer | 資訊架構、互動、響應式、無障礙 | 設計稿與元件規則 |
| Architect | 資料、整合、權限、技術路線 | 技術方案與風險 |
| Developer | 依核准契約實作 | 可執行版本 |
| QA | 流程、資料、桌面、手機與錯誤驗收 | 驗收證據 |

Agent 只接收完成前一階段的必要產出，不把整個私人資料庫或無關上下文傳給外部工具。每次交接記錄輸入、輸出、未決問題與下一步

### 5  開發落地：小步實作與驗收

先完成 P0 的一條端到端流程，再擴充其他畫面。網站至少檢查網址、重整、權限、資料保存與桌面／手機版；行動 App 另檢查安裝、啟動、返回、通知、離線或權限拒絕等已宣稱能力

開發完成不等於交付完成。只有通過實際流程、資料回寫與使用者確認，才能標記為已驗收

## 網站與行動 App 共通檢查

- 入口是否容易再次打開
- 今天最重要的事情是否先出現
- 主要任務是否能在少量步驟完成
- 每個動作是否有成功、失敗、等待與取消回饋
- 資料是否能保存、查詢、備份與復原
- 外部動作是否保留使用者確認
- 手機與桌面是否共用同一份正式資料真相
- 沒有把 mock、截圖或漂亮卡片當成已完成產品

## 開發鎖

以下任一項未確認時，只能整理規格或做本機草稿：

- PM 開發契約
- 核准設計稿
- MCP 權限與資料範圍
- Agent 分工與交接內容
- P0 驗收流程與本版不做範圍

## 給協作者與開發 Agent 的共同規則

這套流程是系統、網站與行動 App 的專案交接標準。任何人接手，都要能從文件理解問題、設計、工具權限與開發結果，不依賴口頭記憶

新建或重大修改時，PM Skill 與 `grill-me` 一起使用：PM 先建立目標、範圍、P0、平台、資料、權限與驗收骨架，`grill-me` 再一次問一個會改變結果的問題，補齊場景、流程、風險與取捨。若環境沒有獨立的 PM Skill，使用本 Skill 的 PM 階段完成同等工作，不假設不存在的命令或工具

## 八項 UI 設計規範

設計稿至少整理以下 8 項：

| 設計規範 | 必須說清楚 |
| --- | --- |
| 目標用戶 | 誰使用、在什麼設備與情境使用 |
| 核心場景 | 最常發生的任務與使用者目標 |
| 頁面結構 | 首頁、列表、詳細、建立、編輯、設定與返回關係 |
| 大圖比例 | 主視覺、封面、預覽或空狀態的比例與裁切規則 |
| 卡片層級 | 主要、次要、警示、待確認與完成資訊的優先順序 |
| 顏色變量 | 背景、文字、品牌、風險、提醒、成功與互動色彩 |
| 字體層級 | 標題、段落、標籤、數字、輔助文字與行動按鈕 |
| 組件狀態 | 預設、啟用、停用、載入、空白、錯誤、成功與待確認 |

## 高保真設計源文件

設計階段的交付物必須是可編輯、可覆用、可協作的高保真源文件，不是單張 UI 圖片或截圖。至少要包含文字、圖層、資訊卡片、顏色變量、字體層級、間距、卡片樣式、圖表／地圖組件、主要頁面與互動狀態

初版不夠精緻時，先在源文件上調整資訊層級、圖片比例、裝飾密度與整套頁面一致性，再進入 MCP 與程式開發

## MCP 與 D2C 交接

MCP 交接設計稿時，只傳遞完成任務所需的最小內容：頁面結構、設計變量、元件狀態、互動規則、資料欄位、驗收流程與設計源文件位置。正式資料寫入、發布、通知、部署、刪除或付款仍需使用者確認

D2C 代表 Design to Code 的設計到程式交接。Agent 先依設計源文件整理頁面、元件、變量、狀態與資料欄位，再生成專案程式或代碼；產出仍需依實際技術棧、資料真相、權限與測試規則調整，不把設計稿或範例代碼當成可上線產品

## 協作者交接格式

```text
目前階段：PM／設計稿／MCP／Agent 規劃／開發／驗收
已完成：
目前輸入：
預期輸出：
未決問題：
權限與敏感資料邊界：
下一步：
```

若設計源文件、MCP 權限、資料真相或驗收條件缺失，接手者先回報缺口，不自行補猜
